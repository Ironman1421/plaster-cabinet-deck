Tinker,
cast in plaster

A working manual for fine-tuning open models with Thinking Machines Lab's training API, checked against its documentation on 16 November 2026.

Eighteen plates. Each is a plaster model, ray-marched live by one GLSL shader on your graphics card, and each can be turned by hand. Move between plates with the ← → keys, a swipe, or the loss curve below.

You write the loop.
They run the GPUs.

Tinker is a cloud training API. Your Python training loop runs on your own CPU machine. Each call ships a batch to Thinking Machines' GPU clusters, which run the forward pass, the backward pass and the optimiser step on a LoRA adapter of an open-weight model.

  • Model sizesLoRA training from 1B to over 1T parameters, dense and Mixture-of-Experts, text and vision.
  • Training methodsSupervised fine-tuning, reinforcement learning (GRPO, PPO), DPO and distillation. Write your own loop or use the cookbook's.
  • Catalogue39 entries on the pricing page on 16 November 2026, long-context variants counted separately: Inkling, Nemotron, GLM, Kimi, Qwen, gpt-oss and DeepSeek.
  • What you keepCheckpoints you can sample on Tinker, or download and merge into an ordinary Hugging Face model.

Fine-tune for behaviour,
not for facts

  • Prompt first. If a good system prompt and a few examples get you there, stop. Nothing to train, nothing to host.
  • Retrieve when the gap is knowledge. Prices, policies and documents change. Retrieval-augmented generation (RAG) updates an index, not weights.
  • Fine-tune when the gap is behaviour. A voice, a strict format, a narrow skill, a classifier, or a long prompt you resend on every call. Tinker's prompt distillation recipe trains a model to act as if that prompt were present.
  • Reinforce when you can score but can't write the answer. If a program can grade an output (tests pass, the maths checks out), RL learns from those grades.

This ladder is our editorial rule of thumb, not Tinker documentation. The reason LoRA suits the third and fourth steps is Thinking Machines' own: post-training data is small and narrow, so low-rank capacity is often enough.

Freeze W.
Learn two thin matrices.

W′ = W + α⁄r · B·A

Low-Rank Adaptation keeps every original weight fixed. For each weight matrix it trains B (d × r) and A (r × k), where the rank r is small. Tinker's default rank is 32, and Thinking Machines' experiments keep α = 32.

r = 32 · 4.18 Btrainable parameters on Inkling 2 Small, all layers: 0.70 % of its 594 B

Count = r × 130,618,176, the per-rank LoRA parameter count in the cookbook's hyperparam_utils.py for Inkling 2 Small (MLP 128.07 M + attention 2.35 M + unembedding 0.21 M). Per pass, LoRA needs a little over ⅔ of full fine-tuning's arithmetic, and one worker pool can train many adapters on one shared base model.

Five rules for LoRA
that save a week

  1. Raise the learning rate about 10× over what full fine-tuning would use. The cookbook's helper returns exactly 10, and the best rate does not depend on rank. Reusing a full fine-tuning rate makes LoRA look worse than it is.
  2. Adapt every layer, especially the MLP and MoE layers. Attention-only LoRA underperforms, even at matched parameter count.
  3. RL needs little capacity. LoRA matched full fine-tuning on RL even at rank 1 in Thinking Machines' tests.
  4. Big supervised datasets need more rank. A rough rule: LoRA parameters ≥ the number of completion tokens you train on.
  5. Avoid huge batches. LoRA pays a loss penalty at large batch sizes, and more rank doesn't fix it.

0.50: the bead reaches the deep basin.

One pool, one clock,
many adapters

When you create a training client, Tinker assigns your job to a worker pool: machines that run forward-backward passes over and over, in lock-step.

  • Your machineHolds the data, the loop, the reward code and the decisions. Needs no GPU.
  • Their poolEach clock cycle runs one forward-backward pass and one optimiser step, covering several LoRA models, often from different users.
  • Why shareThe hardware stays busy even when your batch is small or your loop is idle, and small batches often learn more per example.
  • What it meansA step takes the same time for a big or a small batch, so small batches aren't faster. You pay only for the compute you use.

Submit first,
await later

Every call returns a future at once. The work lands in the next clock cycle that has room. How you await decides how many cycles one training step costs.

fwdbwd = training_client.forward_backward(batch1, "cross_entropy")
optim  = training_client.optim_step(types.AdamParams(learning_rate=1e-4))
nxt    = training_client.forward_backward(batch2, "cross_entropy")
fwdbwd_result = await fwdbwd     # all three were queued first
await optim
next_result = await nxt

Eight calls
carry the whole API

  • ServiceClient()Entry point. Reads TINKER_API_KEY.
  • create_lora_training_clientPick base_model and rank. Returns a TrainingClient.
  • forward_backward(data, loss_fn)Computes and accumulates gradients. Loss is "cross_entropy" or an RL loss.
  • optim_step(AdamParams)Applies the gradients with Adam.
  • sample(prompt, num_samples, …)Generates text from a SamplingClient.
  • compute_logprobs(prompt)Scores tokens without generating.
  • save_weights_for_samplerWeights only, for sampling and export.
  • save_stateWeights plus optimiser state, for resuming.
import tinker
service = tinker.ServiceClient()
trainer = await service.create_lora_training_client(
    base_model="Qwen/Qwen3.5-4B", rank=16)

for step in range(10):
    fb  = trainer.forward_backward(training_data, "cross_entropy")
    opt = trainer.optim_step(tinker.AdamParams(learning_rate=2e-4))
    await fb
    await opt

sampler = await trainer.save_weights_and_get_sampling_client()

One line of JSONL
per conversation

{"messages": [
  {"role": "user", "content": "Do you ship to Rome?"},
  {"role": "assistant", "content": "Yes, 5–8 days."}]}

A renderer turns messages into the model's own chat tokens. The cookbook then builds a Datum: the input is tokens[:-1], the target is tokens[1:], and a weight says which targets count. Position i predicts token i + 1.

Illustrative tokens, not a real tokenizer's split. train_on_what sets the weights: ALL_ASSISTANT_MESSAGES (the sl_basic recipe's choice), ALL_TOKENS, and also LAST_ASSISTANT_MESSAGE, ALL_MESSAGES, CUSTOMIZED and others.

Show it the answer,
or score its attempts

Supervised (SL)

You supply the target text. Loss cross_entropy, inputs target_tokens and weights. It learns in proportion to the tokens you show it.

Reinforcement (RL)

You supply prompts and a reward function. Sample a group per prompt, score each, and set advantage = reward minus the group's average. Losses: importance_sampling, ppo, cispo, dro, gspo, and stable_reinforce (alpha).

types.Datum(
    model_input=types.ModelInput.from_ints(tokens=seq[:-1]),
    loss_fn_inputs=dict(
        target_tokens=seq[1:],
        logprobs=[0.0]*n_prefix + sampling_logprobs,   # from the sampler
        advantages=[0.0]*n_prefix + advantages))       # 0 masks a position

Why RL fits tiny adapters: a policy-gradient episode teaches roughly one bit, while supervised learning teaches in proportion to its tokens (LoRA Without Regret).

Sample, evaluate,
take the weights home

  • save_stateWeights and optimiser state, at tinker://<run>/weights/<name>. Use it to resume.
  • save_weights_for_samplerWeights only, at …/sampler_weights/<name>. Sample it, or open it in the Playground.
  • save_weights_externalWeights for use outside Tinker, at …/external_weights/<name>. Download with signed URLs or the CLI.

Mid-run, save_weights_and_get_sampling_client() gives you a sampler on the current weights. The beta OpenAI-compatible endpoint accepts a tinker://…/sampler_weights/… path as the model name. The cookbook's run_benchmark covers suites such as GSM8K, IFEval, MBPP, LiveCodeBench, SWE-bench and Terminal-Bench.

tinker checkpoint download tinker://<run_id>/external_weights/step-100 --output ./models/
# or merge a LoRA adapter into a plain Hugging Face model in Python:
#   weights.build_hf_model(base_model=..., adapter_path=..., output_path="./merged_model")
vllm serve ./merged_model

Storage is free up to 100 GB or 100 checkpoints per organisation, whichever comes first (since 4 November 2026). On the paid plan all of it costs $0.10 per GB per month. With no TTL a checkpoint is kept until you delete it; ttl_seconds sets an expiry.

Inkling 2 Small,
eleven days old

Thinking Machines' newest model, announced 5 November 2026 and trainable on Tinker from day one. Only 17 B of its 594 B parameters run for each token, about 2.9 %.

  • ArchitectureMixture-of-Experts, 594 B total, 17 B active. Text and image input (292 M-parameter vision encoder), variable effort. No audio.
  • WeightsOpen since 12 November 2026: on Hugging Face as thinkingmachines/Inkling-2-Small. The launch post promised an Apache 2.0 licence.
  • Training on Tinker$1.50 per million tokens at 64 K context, $3.00 at 256 K. Same ID on Tinker as on Hugging Face.
  • Serverless (beta)$0.30 input, $0.03 cached input, $1.00 output per million tokens, 256 K context. Steadier throughput is by waitlist.
  • ElsewhereRuns in vLLM, SGLang and Unsloth; hosted by NVIDIA, Fireworks, Together, Baseten, Nebius, Modal and Cloudflare (12 November update).
  • Their claimsArtificial Analysis Intelligence Index 31. Learns faster than earlier Inkling models on the same data: it matched Inkling-Small's final score on a financial-summarisation task in 75 steps. Known weak spots: wordy, weaker at chat layout, picks tools poorly in big codebases.

Where runs
get stuck

  1. Awaiting every call. Submit-then-wait costs 2 to 3 clock cycles per step; pipelined submission costs 1.
  2. Your own timeouts and retries. Don't wrap sample() in asyncio.wait_for or add retry loops. The SDK already retries, and a slow minute is normal because Tinker is tuned for throughput, not latency.
  3. The wrong learning rate. LoRA wants about 10× a full fine-tune's. The cookbook's get_lr raises NotImplementedError for Inkling models, so sweep the rate yourself.
  4. A mismatched renderer. Take the tokenizer and the renderer from the model name, as the cookbook's model_info.get_recommended_renderer_name does, for training and for sampling alike.
  5. Extra keys in RL data. The RL losses accept exactly target_tokens, logprobs and advantages. Sending weights too is rejected by the server.
  6. Vanishing checkpoints. The cookbook's periodic saves default to a 7-day TTL; only the final one is kept indefinitely. On the free storage plan a session stops once you pass 100 GB or 100 checkpoints.
  7. No payment method. Add billing details before your first train or sample call.

First project:
teach it your FAQ

Goal: a model that answers questions the way David does: his facts, his tone, his length. Collect 200 to 500 real question-and-answer pairs from emails, a help page or your writing. That count is our suggestion for a first run, not a Tinker requirement.

uv init faq-tune && cd faq-tune
uv add tinker tinker-cookbook
uv run tinker auth login        # or: export TINKER_API_KEY=...

Then train it: one file

import asyncio
from tinker_cookbook import cli_utils, model_info
from tinker_cookbook.renderers import TrainOnWhat
from tinker_cookbook.supervised import train
from tinker_cookbook.supervised.data import FromConversationFileBuilder
from tinker_cookbook.supervised.types import ChatDatasetBuilderCommonConfig

MODEL = "Qwen/Qwen3.5-9B-Base"
renderer = model_info.get_recommended_renderer_name(MODEL)

data = FromConversationFileBuilder(
    file_path="faq.jsonl", test_size=30,        # hold 30 out for test/nll
    common_config=ChatDatasetBuilderCommonConfig(
        model_name_for_tokenizer=MODEL, renderer_name=renderer,
        max_length=4096, batch_size=16,
        train_on_what=TrainOnWhat.ALL_ASSISTANT_MESSAGES))

config = train.Config(
    log_path=cli_utils.runs_path("faq-sft"), model_name=MODEL,
    recipe_name="faq_sft", renderer_name=renderer, dataset_builder=data,
    learning_rate=2e-4, lora_rank=32, num_epochs=3,
    eval_every=5, save_every=10)

asyncio.run(train.main(config))

Run uv run python train_faq.py. Logs and checkpoint paths land in ~/tinker-runs/faq-sft. At 300 examples × 250 tokens × 3 epochs on Qwen3.5-9B-Base ($1.463/M), training costs about $0.33 (our estimate). To try Inkling 2 Small, set MODEL = "thinkingmachines/Inkling-2-Small" and choose the learning rate yourself.

Then prove it learned

  1. Watch the held-out loss. With test_size=30 the run logs test/nll every 5 steps. It should fall, then flatten. If training loss keeps falling while test loss rises, it's memorising: stop earlier or add data.
  2. Ask new questions. Put your 20 fresh questions and ideal answers in faq_heldout.jsonl, then sample base and tuned side by side.
  3. Grade with a rubric. Facts right? Sounds like you? Right length? Would you send it unedited? Count the yeses for each model.
import asyncio, json, tinker
from tinker import types
from tinker_cookbook import cli_utils, model_info, renderers
from tinker_cookbook.checkpoint_utils import load_checkpoints_file
from tinker_cookbook.tokenizer_utils import get_tokenizer

MODEL = "Qwen/Qwen3.5-9B-Base"
r = renderers.get_renderer(model_info.get_recommended_renderer_name(MODEL),
                           get_tokenizer(MODEL))
tuned_path = load_checkpoints_file(cli_utils.runs_path("faq-sft"))[-1].sampler_path

async def main():
    service = tinker.ServiceClient()
    models = {"base":  await service.create_sampling_client(base_model=MODEL),
              "tuned": await service.create_sampling_client(model_path=tuned_path)}
    params = types.SamplingParams(max_tokens=300, temperature=0.7,
                                  stop=r.get_stop_sequences())
    for line in open("faq_heldout.jsonl"):
        msgs = json.loads(line)["messages"]
        prompt = r.build_generation_prompt(msgs[:-1])
        print("Q:", msgs[-2]["content"])
        for name, client in models.items():
            out = await client.sample(prompt=prompt, num_samples=1, sampling_params=params)
            print(f"  {name}:", r.parse_response(out.sequences[0].tokens)[0]["content"])
        print("  you: ", msgs[-1]["content"])

asyncio.run(main())

Happy with it? Download the sampler weights with weights.download(...), merge with weights.build_hf_model(...) and serve with vllm serve ./merged_model.
